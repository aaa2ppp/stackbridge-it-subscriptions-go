## Быстрый старт

### Клонирование репозитория

```bash
git clone https://github.com/aaa2ppp/stackbridge-it-subscriptions-go.git
cd stackbridge-it-subscriptions-go
```

### Переменные окружения

Пример всех используемых переменных окружения находится в файле [`dot.env.example`](./dot.env.example).  
Скопируйте его и отредактируйте под свои нужды:

```bash
cp dot.env.example .env

# Сгенерировать случайный пароль для базы данных
echo -e "\nDB_PASSWORD='$(head -c16 /dev/urandom | base64)'" >> .env
```

### Локальный запуск

```sh
# Загрузить переменные окружения
source dev-env

# Установить зависимости и проверить утилиты (при необходимости будут установлены)
make deps check-tools

# Запустить приложение
make run
```

### Запуск в Docker

```sh
# Запустить приложение в контейнере
make docker-run
```

### Swagger

По умолчанию Swagger доступен на [http://localhost:8080/swagger/](http://localhost:8080/swagger/)

### Уборка

```sh
# Удалить контейнеры и том базы данных
make docker-down-volumes

# Удалит локально собранные бинарники и временные файлы
```

## Ограничения, особенности и отступления от ТЗ

### 1. Бессрочные подписки (`end_date`)

В ТЗ указано: *"Опционально дата окончания подписки"*.

**Реализация:**
- В БД поле `end_date` имеет тип `date NOT NULL` (оптимизация, отказ от `NULL`)
- Для обозначения "бессрочности" используется дата `12-9999` (декабрь 9999 года)
- В API запросах:
  - Если `end_date` не указан → подписка считается бессрочной (`12-9999`)
  - Если указан `null` → подписка считается бессрочной (`12-9999`)
  - Если указана конкретная дата → подписка действует до этой даты

**Почему так:**
- Отказ от `NULL` упрощает работу с датами в коде и запросах
- `12-9999` гарантированно не наступит в обозримом будущем
- При необходимости можно прозрачно скрыть это от клиента через DTO, но текущий подход проще и надежнее

### 2. Расчет суммарной стоимости (`total_cost`)

Подписки считаются активными **полными месяцами** в заданном периоде.

**Формула:** `сумма(количество_месяцев_активности * цена_подписки)`

**Пример:**
- Подписка: цена 400 руб., начало 07-2025, конец 12-2025
- Запрос: с 07-2025 по 08-2025
- Результат: 2 месяца × 400 = 800 руб.

**Важно:** 
- Для бессрочных подписок (`12-9999`) расчет идет до `to_date` из запроса
- При необходимости расчета с дробностью в днях требуется уточнение бизнес-логики

### 3. Индексы в БД

Добавлен индекс для оптимизации частых запросов:

```sql
CREATE INDEX idx_subscription_user_id_end_date_active 
    ON subscription (user_id, end_date) 
    WHERE deleted IS NULL;
```

**Предположения:**
- Преобладают запросы активных подписок конкретного пользователя
- Часто используется фильтрация по `user_id` и `end_date`

Для тонкой настройки требуется анализ реальной нагрузки и паттернов запросов.

### 4. Оптимистичная блокировка

При обновлении подписки используется поле `updated` для предотвращения конкурентных изменений (optimistic locking).

Если два запроса пытаются обновить одну подписку одновременно:
- Первый успешно обновляет запись (меняется `updated`)
- Второй получает ошибку `409 Conflict` с текущим состоянием подписки

Это гарантирует целостность данных без использования тяжелых блокировок.

### 5. Обновление подписки (PATCH)

При обновлении подписки можно изменить:
- `service_name` — название сервиса
- `price` — стоимость
- `start_date` — дата начала
- `end_date` — дата окончания

`user_id` не подлежит изменению — подписка жестко привязана к пользователю.

### 6. Фильтрация по датам

- `from_date` — опционально, по умолчанию `01-0001` (с начала времен)
- `to_date` — опционально:
  - Для `GET /subscriptions` — по умолчанию `12-9999` (до конца времен)
  - Для `GET /subscriptions/total` — по умолчанию текущий месяц
